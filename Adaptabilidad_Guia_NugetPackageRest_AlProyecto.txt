================================================================================
Adaptabilidad de la guia NugetPackage_Rest a MedicalAppointments_v2
Cliente HTTP fluido para microservicios .NET, aplicado al dominio de Citas
================================================================================

1. QUE PIDE LA GUIA Y QUE PIDE NUESTRO PROYECTO
--------------------------------------------------------------------------------
La guia entrega una libreria (NugetPackageRest 2.2.0) y un caso de estudio de
tienda en linea con 4 servicios: Pedidos (5001), Pagos (5002), Inventario (5003)
y Reportes (5004), mas una pasarela de pagos externa con OAuth 2.0.

Nuestro proyecto es un sistema de citas medicas con 2 microservicios:
  - Citas     (src/, SQL Server)      agenda y estado de las citas
  - Pacientes (MicroservicioPacientes/, InMemory)  datos del paciente

Ninguno de los servicios de la guia existe aqui. La guia, sin embargo, no exige
un dominio concreto: exige un COMPORTAMIENTO de integracion (seccion 3.16). Por
eso seimplemento la libreria tal cual (Parte I, sin cambios) y se adapto el caso
de estudio (Parte II) al flujo real que ya teniamos: Citas consulta a Pacientes.

Regla que guio la adaptacion: no inventar requisitos que el proyecto no tiene. Cada
pieza de la guia se implemento solo si el proyecto la necesita, y se documento
que queda disponible si aparece la necesidad.

3. NECESIDADES REALES DEL PROYECTO QUE MOTIVARON CADA PARTE
--------------------------------------------------------------------------------
 3.1 Necesidad: verificar que el paciente de una cita exista
     El dominio tiene Cita.PacienteID, pero el dato del paciente vive en otro
     microservicio. Sin cliente HTTP, el detalle de una cita no podia mostrar
     nombre ni documento.
     Respuesta: IPacienteService (Core) + PacienteService (Persistence) +
     endpoint GET /api/citas/{id}/paciente.

 3.2 Necesidad: no repetir el manejo de errores HTTP en cada consumidor
     Un 404 de Pacientes es un resultado de negocio; un 500 o una caida son
     fallas tecnicas. Sin una excepcion propia habia que adivinar con el codigo.
     Respuesta: ApiException con ApiFailureReason (Network, Timeout, HttpError,
     Deserialization) y su traduccion a PacienteNoDisponibleException.

 3.3 Necesidad: que el dominio no dependa de HTTP
     Respuesta: la interfaz IPacienteService vive en Core; Core no importa
     NugetPackage_Rest. Solo Persistence conoce la libreria.

 3.4 Necesidad: que la URL del otro servicio no quede fija en el codigo
     Respuesta: PacientesOptions enlazado a la seccion "Pacientes" de
     appsettings.json, leido con IOptions<T>.


4. DISENO DE BASE DE DATOS Y COMO SE USA CADA TABLA Y CAMPO
--------------------------------------------------------------------------------
El proyecto tiene dos fuentes de datos distintas, y la guia aporta valor en
una sola de ellas: la comunicacion entre bases, no el acceso a la base.

 4.1 Microservicio de Citas - SQL Server, cadena de conexion "CitasDB"
     Contexto: CitasDbContext (ApplyConfigurationsFromAssembly)

     Tabla Citas (entidad Cita)
       Campo               Tipo        Notas de uso
       ---------------------------------------------------------------------------
       CitaID              bigint      PK, identity. Es el id de la ruta
                                        /api/citas/{id}.
       PacienteID          bigint      Obligatorio. FK logica hacia el otro
                                        microservicio: NO hay llave foranea
                                        en la base, porque el paciente esta
                                        en otra base de datos. Esa es
                                        justamente la razon de existir del
                                        cliente HTTP.
       MedicoID            int         Obligatorio.
       EspecialidadID      int         Opcional.
       ConsultorioID       int         Opcional.
       EstadoCitaID        int         Obligatorio. FK -> Estados_Cita.
       FechaHoraInicio     datetime    Obligatorio. Campo natural para ordenar
                                        y filtrar por rango.
       FechaHoraFin        datetime    Opcional.
       Motivo              nvarchar    Opcional, max 1000. Campo de texto
                          (1000)      donde el filtro dinamico destaca:
                                        filter=Motivo.Contains("general").
       Observaciones       nvarchar    Opcional, max 1000. Segundo campo de
                          (1000)      texto para el filtro dinamico.
       UsuarioCreacionID   int         Opcional. Quien creo el registro.
       FechaCreacion       datetime    Automatica, util para ordenar.

     Tabla Estados_Cita (entidad EstadoCita)
       Campo               Tipo        Notas de uso
       ---------------------------------------------------------------------------
       EstadoCitaID        int         PK, identity.
       Codigo              nvarchar    Obligatorio, max 30, indice UNICO.
                          (30)         Sirve para filtrar por codigo
                                       estable (filter=Codigo == "PRO") en
                                       lugar del id, que puede cambiar.
       Nombre              nvarchar    Obligatorio, max 100. Etiqueta legible
                          (100)       para el cliente.

     Campos que la guia NO toca: ninguno. Esta tabla se consulta solo con
     Nuget.Persistence (fase anterior). La guia aporta el puente HTTP, no el
     acceso a datos.

 4.2 Microservicio de Pacientes - InMemory, base "PacientesDb"
     Contexto: ApplicationDbContext
     Este servicio es el que Citas consume por HTTP.

     Tabla Pacientes (entidad Paciente)
       Campo               Tipo        Notas de uso
       ---------------------------------------------------------------------------
       Id                   int         PK. OJO: el id del otro microservicio
                                       es int, mientras Cita.PacienteID es
                                       bigint. La conversion ocurre en la
                                       frontera HTTP y por eso el DTO
                                       GetPacienteExternoDto declara Id como
                                       int.
       Nombre              string      Se devuelve en el GET.
       Apellido            string      Se devuelve en el GET.
       DocumentoIdentidad  string      Identificador funcional. Permite
                                       consultar por documento usando el
                                       filtro dinamico del propio
                                       microservicio:
                                       GET /api/pacientes/one?filter=
                                       DocumentoIdentidad == "12345678-9"
       FechaNacimiento     DateTime    Se devuelve en el GET.

     Tabla HistorialesMedicos (entidad HistorialMedico)
       Campo               Tipo        Notas de uso
       ---------------------------------------------------------------------------
       Id                   int         PK.
       PacienteId           int         FK -> Pacientes. Relacion 1 a muchos.
       FechaRegistro        DateTime    Fecha de la atencion.
       Diagnostico          string      Texto clinico.
       Tratamiento          string      Texto clinico.

     Decision de diseno: GetPacienteExternoDto NO expone Historiales, aunque el
     endpoint las carga. Razon: el historial medico es sensible y pesa; el
     detalle de una cita solo necesita identidad del paciente. Si mas adelante
     se requiere, se agrega el campo al DTO y se resuelve con un endpoint
     especifico del microservicio de Pacientes.


5. QUE APORTA CADA LIBRERIA DEL PROYECTO (nuggets/)
--------------------------------------------------------------------------------
 Problema del proyecto        Libreria que lo resuelve
 ---------------------------------------------------------------------------
 Acceso a datos en la propia   Nuget.Persistence (fase anterior)
 base: paginacion, filtro y    Repository<,>, GetPagedAsync con OrderBy
 ordenamiento genericos        dinamico, GetOneByAsync, AddRangeAsync
                               EF Core 9.0.0 + System.Linq.Dynamic.Core 1.7.4
 ---------------------------------------------------------------------------
 Comunicacion entre microser- NugetPackageRest (esta fase)
 vicios por HTTP               IRest con cadena fluida, ApiException,
                               ApiFailureReason, typed client
                               Newtonsoft.Json 13.0.4 + Serilog 4.3.0

 Son complementarias y no se pisan: la primera habla con la base de datos
 (EF Core, IQueryable), la segunda con otros servicios (HttpClient). Juntas
 cubren los dos problemas de una arquitectura de microservicios.

 Nota sobre el dominio de datos: Nuget.Persistence usa System.Linq.Dynamic.Core
 para traducir el texto del filtro a IQueryable, de modo que el filtro se
 ejecuta en SQL y no trae toda la tabla a memoria. La guia no cambia ese
 comportamiento; solo se le sumo el puente HTTP.


6. ADAPTACIONES TECNICAS CONCRETAS
--------------------------------------------------------------------------------  Elemento de la guia        Adaptacion en nuestro proyecto
 ---------------------------------------------------------------------------
 Paquete: PackageId             NugetPackageRest, en nuggets/NugetPackage_Rest/
 NugetPackageRest               con solucion propia y 17 pruebas xUnit
 Capa Infraestructure           Mapeada a MedicalAppointments.Persistence
 Core                           MedicalAppointments.Core (MediatR y CQRS ya
                                estavam ahi; se agrego AddCore)
 Contrato de negocio            IPacienteService (ObtenerPacienteAsync)
                                en vez de IPagoService
 Sobre de respuesta             Se reutilizo Nuget.Persistence.Common.
                                HttpResponse<T> en vez de crear otro
 Envoltura de error             PacienteNoDisponibleException (Core) en vez
                                de DomainException, para no duplicar el
                                concepto que ya existe en el proyecto
 DTO con [JsonProperty]         GetPacienteExternoDto, porque la libreria
                                serializa con Newtonsoft y no con
                                System.Text.Json
 Handler que traduce fallas     GetCitaPacienteQueryHandler convierte
                                PacienteNoDisponibleException en
                                ValidationException y el controller responde
                                400, igual que el resto de endpoints
 Timeouts                       client.Timeout = 30 s en AddHttpClient, en
                                vez del default de 100 s
 Registros en Serilog           Activados con EnableRequestLogs en
                                appsettings.json de la API


7. LO QUE NO SE IMPLEMENTO Y POR QUE
--------------------------------------------------------------------------------
 - Ejercicios 1 a 5 de la seccion 4 (CancellationToken, WithQuery,
   serializador intercambiable, Polly, pruebas multipart): son ejercicios de
   la libreria, no necesidades del proyecto. Quedan disponibles.
 - Microservicio de Notificaciones (ejercicio 6): el proyecto no lo necesita.
 - Registro del feed local en la configuracion global de NuGet: aqui la
   libreria y los microservicios viven en el mismo repositorio, asi que se
   consumio por ProjectReference (opcion D de la guia), sin tocar la
   configuracion de la maquina.
 - Serilog en la API: la libreria escribe en el logger estatico de Serilog; si
   la API no configura un sink, esos registros se descartan. Se dejo el
   ILogger de ASP.NET porque el proyecto ya tiene su logging.

9. CONVENCION DE ARQUITECTURA QUE SE MANTIENE
--------------------------------------------------------------------------------
La arquitectura del proyecto se mantiene en capas, con los rasgos de Clean
Architecture y CQRS, con hexagonalidad posible (inversion de dependencias):
las interfaces de las capas internas (ICitaRepository en Domain,
IPacienteService en Core) y las implementaciones en las capas externas
(Persistence). La guia se integro dentro de esta convencion y no al reves: su
capa Infraestructure se mapeo a nuestra capa Persistence.

Lo que falta para llamar hexagonal a la estructura completa:
 - MedicalAppointments.Domain referencia Nuget.Persistence, que arrastra EF
   Core y System.Linq.Dynamic.Core a la capa mas interna. El dominio deberia
   depender solo de sus propias interfaces.
 - Los controllers usan ICitaRepository directamente y saltan la capa Core.
Ninguno de los dos puntos bloquea la guia ni los requisitos actuales del proyecto;
quedan como mejora para una fase posterior.
