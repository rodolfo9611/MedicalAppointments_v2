1. QUE SE IMPLEMENTO
--------------------------------------------------------------------------------
La guia pide construir la libreria NugetPackage_Rest (PackageId NugetPackageRest):
un cliente HTTP fluido que envuelve HttpClient en una API encadenada, estandariza
el manejo de errores y se integra con la inyeccion de dependencias.

En este repositorio la libreria quedo junto a la otra libreria compartida del
proyecto, dentro de nuggets/, y se integro en el microservicio de Citas, que
consume por HTTP al microservicio de Pacientes.

El caso de estudio de la guia (tienda en linea: Pedidos, Pagos, Inventario,
Reportes) se sustituyo por el dominio real del proyecto: Citas -> Pacientes.
Se aplicaron los mismos 8 pasos y el checklist 3.16 sobre nuestras capas.

Paquetes (paso 3): Microsoft.Extensions.DependencyInjection.Abstractions 9.0.10,
Microsoft.Extensions.Options.ConfigurationExtensions 9.0.10, Serilog 4.3.0,
Newtonsoft.Json 13.0.4.

Cadena fluida (guia 1.7). El orden de las llamadas lo impone el compilador:

  _rest.Post                     IWithContentRequest
      .WithoutAuth()              IFluentAuth<IFluentFormat>   (autenticacion)
      .WithHeaders(dict)          IFluentAuth<IFluentFormat>   (headers, repetible)
      .WithUri(base, endpoint)    IFluentFormat                (URI obligatoria)
      .WithBody(obj)              IFluentContent               (body: json, form,
                                                                 multipart o ninguno)
      .DeserializeWithAsync<T>(); resultado o ApiException

Etapas terminales (paso 9): DeserializeWithAsync<T>(), GetContentAsStringAsync(),
GetContentAsByteArrayAsync(), y await directo sobre la cadena, que devuelve el
HttpResponseMessage crudo sin validar el codigo.

Manejo de errores (3.12). Cada falla tecnica del otro microservicio recorre esta
cadena, sin que Core conozco la libreria HTTP:

  red/timeout/JSON inválido -> ApiException (libreria, Infrastructure)
                             -> PacienteNoDisponibleException (Core)
                             -> ValidationException (Core)
                             -> HTTP 400 con el diagnostico (Api)

El 404 del otro microservicio NO se considera falla tecnica: PacienteService lo
convierte en null y el endpoint responde 404, que es un resultado de negocio.

Configuracion (appsettings.json del proyecto Api):

  "Pacientes":    { "BaseUrl": "http://localhost:5015" }
  "RestSettings": { "EnableRequestLogs": true }

La base va sin barra final y el endpoint con barra inicial, porque WithUri solo
concatena los dos textos (nota de la guia 3.3).


4. COMO PROBARLO
--------------------------------------------------------------------------------
Requisito: levantar primero el microservicio de Pacientes, porque Citas lo
consume por HTTP.

  Terminal 1 - Microservicio de Pacientes
    dotnet run --project MicroservicioPacientes.Api --urls http://localhost:5015
    Siembra un paciente: Id 1, Carlos Perez, 12345678-9.

  Terminal 2 - Microservicio de Citas
    dotnet run --project src/MedicalAppointments.Api --urls http://localhost:5000

  Llamadas
    GET http://localhost:5000/api/citas/1/paciente      200, paciente del Id 1
    GET http://localhost:5000/api/citas/2/paciente      404, el PacienteID 2 no
                                                         existe en Pacientes
    GET http://localhost:5000/api/citas/9999/paciente   404, la cita no existe
    Con Pacientes detenido:
    GET http://localhost:5000/api/citas/1/paciente      400, Motivo: Network

  Pruebas automatizadas
    dotnet test nuggets\NugetPackage_Rest\NugetPackage_Rest.sln   (17 pruebas)
    dotnet test MedicalAppointments.sln                          (4 pruebas)

  Consumir la libreria en otro microservicio (checklist 3.16)
    1. Infrastructure referencia la libreria y Microsoft.Extensions.Http.
    2. appsettings.json tiene RestSettings y las secciones de URLs.
    3. Core tiene las clases de opciones y services.Configure<T>(...).
    4. Core define una interfaz por servicio remoto, en terminos de negocio.
    5. Infrastructure la implementa inyectando IRest e IOptions<T>.
    6. AddPersistence llama AddRequestLogging y AddHttpClient<IRest, RestBuilder>().
    7. Program.cs llama AddCore(...) y AddPersistence(...).
    8. Los handlers dependen de las interfaces de Core, nunca de IRest.
    9. Las fallas se capturan como ApiException y se traducen a excepcion de Core.
   10. Los DTOs usan [JsonProperty].
   11. Hay pruebas unitarias del servicio con FakeHttpMessageHandler.

NU5026; hay que pasar ese parametro (paso 26).
